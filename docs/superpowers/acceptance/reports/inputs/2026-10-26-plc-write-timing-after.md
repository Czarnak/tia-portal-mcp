## Reading the numbers

- Set A was taken while the machine was noisy: the same worker needed far more item time for identical single-item work (T1 item sum 9.9 s vs 5.2 s baseline; the discarded warm-up T3 took 113 s against 54 s) and the T5 dry run, which makes no Siemens call, took 11.5 s against 6.0 s. Set A therefore overstates every column, including the item sums, which the refactor does not touch.
- Set B ran on a quiet machine (T5 5.8-8.4 s, T1 item 5.2-6.4 s, close to the baseline) and is the cleaner comparison. There, remainder (planning, verification, audit, binding) falls by about 40 percent for T1, T2 and T4 (about 7.3-8.1 s vs 12.7-13.7 s): the pre-checks that walked tag tables and block groups are gone. T5 is unchanged (6.2 s vs 6.0 s) and item sums are within noise.
- T3 remainder rises by 15-21 percent (about 21 s vs 18.4 s). Likely cause (inference): the new content-hash verification of `update_block_logic` (verification `check:"contentHash"`, which re-reads the block after the import); it is the only case where the remainder grew.
- The post-write `contentHash` of the T3 block differs in every run (`ccd8ed9d...`, `fc51b208...`, `ce4b219f...`, `92030d6c...`, `740ececd...`, `5e5ba7b4...`, `f332108a...`) although the written content is identical across runs, so the exported bundle carries a per-run value (inference: a timestamp or generated id). A caller cannot compare the post-write hash with a hash computed from the content it sent.
