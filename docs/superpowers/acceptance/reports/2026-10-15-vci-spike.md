# VCI (version control interface) live spike — 2026-10-15

Result: **the questions that block the `vci_write` design were answered from live evidence on TIA Portal V21
(2100.0.121.1), standalone project only.** Four findings shape the design more than the rest:

1. **Openness VCI works on leaf objects only.** Containers either reject cleanly or **crash the whole Portal**
   (unhandled exception inside Siemens' export command). A scope must be expanded to leaves by the worker.
2. **Scope operations are slow.** A whole-PLC scope (~570 block leaves) is about 8 minutes plain and about 3.5
   minutes in one transaction, against the worker's 5-minute request timeout.
3. **An import (`WorkspaceToProject`) validates nothing.** A malformed SCL file imported without any error and left
   the mapping `Equal`; the block is merely uncompiled and broken.
4. **Siemens' own guards are not enough.** Two exports to the same relative directory and file name overwrote the first
   object's files with no error; the format argument, not any setting, decides what is written.

This is spike evidence, not an acceptance of a shipped feature. The raw logs stay outside the repository.

## Fixture and method

A disposable standalone project (created from a copy, never saved except where a step says so): one S7-1500
software PLC with about 570 blocks (LAD, SCL, F-LAD, global/instance DBs, F-DBs, UDTs, technology objects, tag
tables) in about 8 user block groups, a second PLC with one block named like a block in the first, a Unified HMI
with one global script module, a classic HMI, and a project library with released types. STL and GRAPH were skipped
by decision. Two workspaces were prepared in the VCI editor before the run: one by dragging a whole PLC device, one by
dragging a block folder.

A throwaway .NET Framework 4.8 console harness drove `Siemens.Engineering.VersionControl` through the Openness API.
It attached only to the UI-mode Portal with the disposable project open, never disposed the Portal process, never saved,
closed or compiled, and confined every file write to a sandbox directory. Every call was traced before it ran.
Settings, global-file and `.vci` folder state were captured read-only. Siemens' crash reports (below) were read after each crash.

## Findings by question

| Q | Finding |
| --- | --- |
| Q0 baseline | The VCI service is available. Both prepared workspaces contain **leaf mappings only**: the whole-PLC workspace has 673 (later 676) leaf mappings, the folder workspace 3. No container mapping exists, and `GetChildStatus()` is null for all 676. Reads are side-effect free: `IsModified` and the file listing are unchanged by status calls. Of the settings Openness exposes only `VCI/ProjectLanguageImportOptions` (Int32); the global export formats and the automatic-assignment flag exist only in the user's `Settings.xml`. |
| Q7 formats | `GetSupportedFileFormats` throws "The Object {0} is not supported" for every container (device, device item, PLC software, block groups, tag/type/technology-object groups, library, library folders, a library type version). On leaves it returns `SimaticML`, `SimaticSD`, plus `SCL` for SCL blocks and `DB` for data blocks. Tag tables and technology-object DBs: `SimaticML` only. |
| Q1 containers | Passing a container to `ExportObject`: user block group, `BlockGroup`, tag-table, type and technology-object groups reject cleanly in 20-45 ms ("specified file format is invalid for object …; take it from `GetSupportedFileFormats`"), with the same text for a valid and a bogus format, no file, no mapping. **A device and the project library crash the Portal** (5-13 s, `NonRecoverableException`). A PLC software, a device item and library type folders were deliberately not tried. The UI itself expands containers to leaf mappings. |
| Q2 settings | The explicit format argument always wins. A consistent LAD block exported as `SimaticML` into a workspace whose own config says LAD = SIMATIC SD (and global LAD = SD) succeeded, and the mapping records `SimaticML`. 147 leaves exported as `SimaticML` into workspaces with no format config. `Workspaces.Create` writes only `workspace.vci.config`, not `exportFormats.config`, so the config is not a snapshot of the global settings. Setting writes and the automatic-assignment matrix were not run (open below). |
| Q3 import | `w2p` works plainly, under `ExclusiveAccess` (148 ms) and inside a transaction (`CanCommit=True`); rolling that transaction back really reverts the block (byte-identical re-export, original dates and consistency restored). The imported object is **recreated**: the old reference is disposed and is no longer equal to the mapping's object after a committed import. An imported SCL block is left **inconsistent** (no compile date). **A malformed SCL file imports without any error.** Library-type import renamed the type to the workspace file name and left the mapping `ProjectObjectChanged`. |
| Q4 transactions | `w2p` is allowed inside a transaction and in a rolled-back one. Thrown item errors inside a transaction leave `CanCommit=False` (a failed batch cannot be committed). A rollback restores the project but not the files written by an export. |
| Q5 timing | 147 leaves exported as `SimaticML`: **128 s plain** (avg 837 ms, max 13.8 s), **58 s in one transaction** (avg 244 ms, commit 1.1 s). `GetStatus()` costs about 460 ms per mapping (49-68 s for 147). Imports take 1-8 s per block (a 548 KB DB: 5.6 s). `sync-all` on all-`Equal` mappings throws for every item. One-block runs carry about 30 s of attach and enumeration overhead. |
| Q6 filesystem | The export directory must start with `\` **and already exist**; the tool never creates it. A non-existent workspace root fails ("Root directory does not exist"). `mapping-delete`, unrooting a workspace and `ws-delete` **keep every file**. Duplicate workspace names throw. Creating a workspace on a leftover folder keeps all files and adopts none. |
| Q8 status | After export: `Equal`. Disk edit: `Unequal/WorkspaceFileChanged`. Project edit: `ProjectObjectChanged` (a TIA rename counts). Both: `ProjectObjectChanged, WorkspaceFileChanged` (a conflict is detectable). File missing: `WorkspaceFileMissing`. After a sync the `Status` property stays stale while `GetStatus()` is right. `Unknown` was not produced. |
| Q9 persistence | Closing without saving drops every unsaved workspace and mapping (their files and `.vci` folders remain as orphans); saving first keeps them across a reopen. |
| Q10 consistency | `SimaticSD` export of an inconsistent LAD block **succeeds**; `SimaticML` and `SCL` refuse it ("object(s) is not consistent"). VCI's consistency check differs from Openness' `IsConsistent`: a block with `IsConsistent=True` and an unchanged compile date was refused as inconsistent in three runs, with and without the Safety login and after a compile. |
| Q13 rename/move/delete | A TIA rename keeps the mapping and the file key; `EngineeringObject` returns the renamed object. A move is invisible (`Equal`). A delete silently removes the mapping and leaves the file. A file renamed on disk is `WorkspaceFileMissing` (no automatic follow). |
| Q14 unlinked files | A new file dropped into a workspace folder is ignored; no Openness path imports it. |
| Q15 same-named blocks | Exporting a second PLC's same-named block to the **same relative directory and file name overwrote the first block's files without error** (12,603 → 257 bytes, resource file deleted) and left the first mapping `WorkspaceFileMissing`. Different directories or file names are the safe form. `ConnectObject` onto an existing file threw. |
| Q16 library types | A type exports four files (`.libinfo`, `.libint`, `.s7dcl`, `.s7res`). Several UDT mappings can share one file. See Q3 for the import side effects. |

## Portal crashes: cause and evidence

The Openness client sees only a generic `NonRecoverableException`. The real exception is in the Portal's own crash report,
`<ProgramData>\Siemens\Automation\Portal V21\Diagnostics\2100.0.121.1\<id>\<id>.dr` (a zip with `ErrorReport.xml`, `Reason="Openness"`),
and the Windows Application log ("Reporting for process Siemens.Automation.Portal … /r:Openness") at the crash second. All four
crashes were an **unhandled `InvalidOperationException` in the VCI export command, wrapped in `EngineeringTargetInvocationException`**:

| Object | Message | Where |
| --- | --- | --- |
| Device, project library | `OpennessBrowsableProvider` does not provide service `IUiRoleProvider` | `ExportObjectCommandLogic.ValidateAndExportObject` |
| One OB in a safety group (SCL, `SimaticSD`), 3 of 3 attempts, also with the Safety login | `DomainEntityWrapper` does not provide service `IExportProvider` | `ExportCommandLogic.PerformExport` ← `Execute` ← `ExportObjectCommandLogic.ExportObject` |

The same OB with `SimaticML` never crashed; it was refused as not consistent (3 attempts: no login, after a compile, with the Safety
login), and its compile date never changed. The cause is not the Safety login. It looks like a block VCI cannot export (possibly system-generated);
that last point is a hypothesis.

## Decision table outcome

| Question | Outcome | The design… |
| --- | --- | --- |
| Q0 | reads are side-effect free | VCI status can sit in a read tool and in `dryRun`; cost still needs a budget |
| Q1 | leaf objects only; containers reject or crash | the worker expands a scope to leaves and never passes a non-leaf to `ExportObject`/`ConnectObject`; per-leaf results inside one item |
| Q1b | the UI creates leaf mappings only | no container-mapping sync exists to expose; reads show leaf mappings |
| Q2 | explicit format wins | the tool passes the format explicitly and never reads global or workspace settings |
| Q2 | formats unreadable | the default is the tool's own choice, never the global setting |
| Q3/Q4 | w2p works inside a rolled-back transaction | wrap a call's imports in one transaction; pre-filter to items that can succeed (a thrown error makes `CanCommit` false) |
| Q3 | malformed content imports silently | report "imported, not validated" and point to `compile_check`; no pre-validation exists |
| Q5 | scope operations approach minutes | per-item or chunked requests; budget status reads; one transaction per call is about 2x faster |
| Q6 | deletes keep files | state in the result that files remain; the tool creates export directories itself and uses `\`-rooted paths |
| Q8 | `Status` lags `GetStatus()` | always use `GetStatus()`; sync only items that are not `Equal` |
| Q9 | mappings need a save | results flag `projectModified:true` and tell the agent to call `save_project` |
| Q10 | inconsistency is refused for `SimaticML`/`SCL`; `SimaticSD` can crash an unexportable block | probe with `SimaticML` only (`SCL` is impossible for LAD, FBD, STL, GRAPH); never rely on `IsConsistent`; treat `NonRecoverableException` as Portal-lost, never retry or batch unattended |
| Q13 | file key survives renames | selectors name mappings by file key, not object name; a delete removes the mapping silently |
| Q14 | no import path for unlinked files | documented limitation; create objects with `plc_write`, then connect |
| Q15 | same file key overwrites silently | a block guard on file-key uniqueness and file existence before every export |

## Not executed, or only partly

Retained as evidence limits, not as blockers:

- **Q1:** a PLC software, a device item and library type/user folders were not tried (a device and the library already crash). Syncing and connecting a container into a second workspace is moot because no container mapping exists.
- **Q2:** writing global VCI settings (`set-setting` int and enum, with restore), when the global settings file changes, and the automatic-assignment on/off matrix with renamed and new blocks.
- **Q3/Q4:** a **conflict** (changed on both sides) was observed in status but `w2p` on it was not run; `p2w` in a rolled-back transaction (are the files still written) was not run; the inactive-language import options 0 versus 1 were not compared; the case of a mapped object changed in the project by an unrelated edit was not run.
- **Q8:** the `Unknown` status was not produced (V21 has no `InitializeStatus`).
- **Q10:** the crash-prone OB was not tried with `SCL`; a block that becomes inconsistent in the UI after export was covered only through its status, not through a `p2w`.
- **Q11:** `LicenseNotFoundException` never appeared.
- **Q12:** the library workspace properties (`GlobalLibraryPath`, `DeleteUnusedTypeVersionFromLibrary`) were not exercised on a sandbox copy of a library.
- **Q15:** `connect` of a second PLC's block onto an already mapped file was tried once and threw without detail.
- **Coverage:** no F-CPU separate run, no STL or GRAPH block (skipped by decision), no multiuser or server projects (out of scope).
- A harness defect (directories not created before export) wasted one 513-leaf run; it is fixed in the throwaway harness.
