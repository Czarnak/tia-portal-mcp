# Acceptance Criteria: Phase 5 Reliability and Lifecycle Integrity

**Spec:** `docs/superpowers/specs/2026-07-23-phase5-reliability-lifecycle-integrity-design.md`
**Date:** 2026-07-23
**Status:** Approved

---

## Criteria

| ID | Description | Test Type | Preconditions | Expected Result |
|----|-------------|-----------|---------------|-----------------|
| AC-001 | CI and publish solution builds use serialized MSBuild execution. | Logic | Inspect `.github/workflows/ci.yml`, `.github/workflows/publish.yml`, and invoked build scripts. | Every solution build that triggers host/worker copy targets invokes `dotnet build TiaMcpServer.sln -m:1` or an equivalent serialized form; no parallel solution-build path remains. |
| AC-002 | Coverage configuration measures only the approved instrumentable production assemblies. | Logic | `TiaMcpServer.Tests/coverage.runsettings` and the CI coverage command exist. | Cobertura output includes `TiaMcpServer` and `TiaMcpServer.Contracts`; it excludes test assemblies, `TiaMcpServer.FakeWorker`, generated code, and `TiaMcpServer.OpennessWorker`, and the exclusions are visible in repository configuration. |
| AC-003 | CI enforces an 80% scoped aggregate line-coverage threshold locally. | Logic | Run the coverage command from the spec and execute the CI threshold step against reports with line rates below, equal to, and above `0.80`. | The threshold step exits non-zero below `0.80` and exits zero at or above `0.80`; Codecov remains reporting-only. |
| AC-004 | Phase 5 preserves the persistent two-process, single-request worker architecture. | Logic | Inspect host registration, `PersistentWorkerTransport`, and worker startup after the changes. | The .NET 8 host still communicates with one persistent net48 worker over NDJSON, and worker requests remain serialized by one gate. |
| AC-005 | Phase 5 preserves the approved MCP tool surface. | Logic | Generate or inspect MCP tool metadata and schemas. | Exactly 10 MCP tools and exactly 7 lifecycle tools are exposed; the internal lifecycle probe and injected service parameters do not appear in MCP schemas. |
| AC-006 | A direct status request for project B cannot open or switch away from already-open project A. | API | Real TIA Portal V21 has project A open; the MCP session is unbound; disposable project B exists. | `get_project_status(projectPath=B)` returns a failure whose message states that read operations do not switch projects; project B is not opened, project A remains active, and host binding does not change. |
| AC-007 | A direct status request does not open a supplied project when no project is open. | API | Real TIA Portal V21 has no project open; MCP session is unbound; caller supplies a valid project path. | The response has `isOpen:false`; no project is opened or bound. |
| AC-008 | A direct status request inspects only the already-open project. | API | Real TIA Portal V21 has project A open; MCP session is unbound; caller omits `projectPath`. | The response reports project A; no open/switch command is issued, and host binding remains null. |
| AC-009 | Guarded lifecycle writes use the internal state probe rather than user-facing status. | API | FakeWorker records worker operation names for save, save-as, archive, and close preview/apply flows. | Every preview and apply state read uses the internal probe operation; none invokes the direct status operation; the internal probe is not MCP-callable. |
| AC-010 | Existing guarded lifecycle preview/apply flows remain functional after the probe split. | API | Real TIA Portal V21 uses a disposable project copy. | Save, archive, close, and supported SaveAs each produce a preview token and succeed on a matching apply with `confirm=true`; token and audit behavior remain intact. |
| AC-011 | A failed lifecycle worker call does not change session binding. | Logic | Host is bound to canonical path A; worker returns failure for a lifecycle operation. | `ProjectSessionBinding.BoundProjectPath` remains canonical path A. |
| AC-012 | A successful read does not bind an unbound session. | Logic | Host is unbound; worker returns a successful direct status response with a resolved path. | `ProjectSessionBinding.BoundProjectPath` remains null after the read. |
| AC-013 | Successful lifecycle transitions bind only to worker-reported ground truth. | Logic | A successful open, create, or rebind-capable lifecycle response contains `ResolvedProjectPath=X`, while caller input differs from X. | Host binding changes only after success and becomes canonical X; caller input is never used as fallback ground truth. |
| AC-014 | A lifecycle transition requiring rebinding fails when no resolved path is returned. | Logic | Worker reports operation completion without the required `ResolvedProjectPath`. | Response category is `postcondition_failed`, and host binding does not adopt caller input or target intent. |
| AC-015 | `save_project_as(rebind:false)` is rejected before preview and execution. | API | Invoke `save_project_as` with otherwise valid inputs and `rebind:false`; worker invocation count is observable. | Response category is `validation_error`; no safety token is issued, Siemens `SaveAs` is not invoked, and binding is unchanged. |
| AC-016 | Supported SaveAs binds host and worker to the copied project. | API | Real TIA Portal V21 has source project A open; caller completes preview/apply with `rebind:true`; copied path is B. | Apply invokes Siemens once, succeeds, and leaves both host and worker bound to canonical path B. |
| AC-017 | Failed SaveAs preserves the original binding. | API | Host is bound to A; FakeWorker returns a SaveAs failure before a successful completion. | Host binding remains canonical path A and does not adopt source, target, or missing resolved-path values. |
| AC-018 | SaveAs copied-path discovery failure is reported as an unverifiable outcome. | Logic | Siemens `SaveAs` returns, but the worker cannot establish the copied project path. | Response category is `postcondition_failed`; response warns that project state may have changed; host does not bind to the target intent. |
| AC-019 | Successful direct lifecycle responses preserve worker warnings. | API | FakeWorker returns success plus one or more warnings for a direct lifecycle request. | The MCP result remains successful and contains the warnings separately from the primary payload. |
| AC-020 | Warnings do not mask lifecycle failures. | Logic | Worker returns a categorized failure plus warnings. | The failure category remains the primary outcome; warnings are additive and do not convert the result to success. |
| AC-021 | Direct warning propagation obeys the existing response budget. | Logic | Worker returns more warnings and warning text than the configured limits. | The result contains no more than the configured warning count and size; truncation is explicit and the primary outcome is preserved. |
| AC-022 | Safety-token protections remain unchanged by lifecycle routing changes. | API | Exercise missing token, invalid token, `confirm=false`, changed input, changed project path, reordered operations, and changed current state. | Every case fails before write execution; a valid single-use token succeeds once and cannot be reused; audit output is written only through existing guarded paths. |
| AC-023 | Block-bundle parsing rejects missing and duplicate logical documents before import. | Logic | Provide bundles with a missing document name and with duplicate logical names. | Each bundle returns `validation_error`; no file staging or Siemens import occurs. |
| AC-024 | Block-bundle staging rejects unsafe filenames and paths. | Logic | Provide rooted paths, traversal segments, separator-based escapes, and filenames resolving outside the operation temp directory. | Each input returns `validation_error`; no file is written outside the temp directory and Siemens import is not invoked. |
| AC-025 | Block-bundle staging uses deterministic exact filenames. | Logic | Parse a valid multi-document bundle twice into two fresh temporary directories. | Both runs produce the same ordered descriptor list; every materialized filename exactly matches the filename passed to `ImportFromDocuments`; every referenced file exists before import. |
| AC-026 | A byte-identical `update_block_logic` round trip succeeds against TIA Portal V21. | API | Export a known block from a disposable live project and submit the unmodified bundle. | The operation succeeds once, the block remains semantically unchanged, and compile or re-export verification succeeds. |
| AC-027 | A valid edited `update_block_logic` round trip succeeds and compiles. | API | Edit a known block bundle without removing required documents and apply it to a disposable live project. | The operation succeeds once; re-export reflects the edit and the target block compiles successfully. |
| AC-028 | Malformed block input does not produce ambiguous success or alter the original block. | API | Submit each approved malformed-bundle case to a disposable live project and capture the block before and after. | Each call fails in the documented category, never reports success, and byte-equivalent re-export confirms the original block is unchanged. |
| AC-029 | Failed block postcondition verification is a failure, not warning-only success. | Logic | Import returns, but compile or re-export postcondition verification is forced to fail. | Response category is `postcondition_failed`; warnings state that project state may have changed; the result is not successful. |
| AC-030 | SCL block generation always contains a valid non-empty compile unit. | Logic | Generate SCL sources for each Phase 5-supported block type and valid name. | Each generated source contains at least one compile unit for the requested block type/name and passes worker-side structural validation before import. |
| AC-031 | SCL `create_block` succeeds and compiles against TIA Portal V21. | API | Real TIA Portal V21 uses a disposable project, valid group, unused block name, and supported block type. | Creation succeeds once; the block exists at the requested destination and compiles successfully; partial or ambiguous outcomes return failure. |
| AC-032 | Phase 5 failure categories serialize and render deterministically. | Logic | Produce one representative response for `validation_error`, `binding_conflict`, `state_changed`, `worker_operation_failed`, `worker_timeout`, `worker_crashed`, and `postcondition_failed`. | Each response round-trips its exact category and renders the corresponding user-facing recovery message without exposing protected data or raw credentials. |
| AC-033 | A write is never automatically retried after worker timeout. | API | FakeWorker delays a write beyond the request timeout and records request count. | Response category is `worker_timeout`; exactly one write request is issued; message instructs the caller to inspect current state before retrying. |
| AC-034 | A write is never automatically retried after crash or protocol loss. | API | FakeWorker crashes, breaks the pipe, or returns malformed protocol data during separate write scenarios and records request count. | Each scenario returns `worker_crashed` or the documented protocol-loss failure; exactly one write attempt occurs; caller is instructed to inspect state before retrying. |
| AC-035 | Enumerated recoverable failures require no manual TIA Portal recovery. | API | On real TIA Portal V21, execute status binding conflict, rejected `rebind:false`, invalid SaveAs input, malformed bundle rejected before import, and Siemens import failure with worker connected. | After every scenario, a subsequent status/read call succeeds using the same TIA session; crash and timeout are recorded as excluded uncertain-outcome cases. |
| AC-036 | Full automated and Round 4 regression suites remain green. | API | Run restore, serialized Release build, solution tests, coverage collection/threshold, and the complete Round 4 acceptance suite. | Every command exits zero, scoped line coverage is at least 80%, and no Round 4 criterion regresses. |
| AC-037 | Live acceptance evidence identifies the actual Siemens runtime. | API | Execute the Phase 5 live acceptance suite on a disposable project copy. | The acceptance report records Windows version, TIA Portal V21 version, Openness assembly version/path selection, test-project preparation, each AC result, and cleanup outcome. |
| AC-038 | Repository documentation matches delivered Phase 5 behavior. | Logic | Inspect `README.md`, `docs/IMPROVEMENT_PLAN.md`, schemas/descriptions, known issues, and the live acceptance report. | All sources consistently state side-effect-free status reads, internal lifecycle probing, rejected `rebind:false`, repaired block paths, preserved 10-tool surface, and Phase 6 transaction/event deferral; obsolete known-issue claims are removed only after live verification. |
| AC-039 | Source skill documentation is updated without editing installed plugin caches. | Logic | The owning source-skill repository is available and separately authorized; inspect its tool descriptions and local plugin cache status. | Source skill documentation describes the actual batched ten-tool surface and Phase 5 lifecycle contract; installed cache files have no local modifications. |
| AC-040 | Graphify artifacts reflect the final code state. | Logic | Run `graphify update .` after the final code change and identify the commit recorded by `graphify-out/GRAPH_REPORT.md`. | `graphify update .` exits zero, and `git diff --quiet <recorded-graph-commit> HEAD -- '*.cs'` exits zero before completion. |
| AC-041 | Phase 5 introduces no hardcoded secrets or protected data leakage. | Logic | Scan the full branch diff and inspect new warnings, audit fields, tests, workflows, and documentation. | Secret-pattern scan returns zero findings; no credentials, tokens, passwords, or protected-project content is added to logs, warnings, audit output, fixtures, or docs. |
| AC-042 | All changed external inputs are validated at host and worker boundaries. | Logic | Review changed lifecycle and block-write inputs plus their negative tests. | Every changed input has an explicit validation path; invalid project paths, `rebind:false`, malformed bundles, and unsafe filenames fail deterministically before unsafe execution. |
| AC-043 | Phase 5 preserves audit semantics and avoids uncertain-outcome false success. | Logic | Exercise successful, validation-failed, worker-failed, timeout/crash, and postcondition-failed guarded writes. | Audit entries preserve existing operation/input/state binding; no timeout, crash, or postcondition failure is recorded or returned as successful completion. |
| AC-044 | Phase 6 capabilities remain outside Phase 5 production scope. | Logic | Review the Phase 5 production diff and generated MCP schemas. | No new Openness `Transaction`, `ExclusiveAccess`, authentication-event, event-subscription, server-push, long-polling, or MCP `doctor` capability is introduced. |
| AC-045 | A bound direct status read surfaces worker-path divergence without adopting it. | Logic | Host binding is canonical path A; FakeWorker returns a successful direct status response with canonical `ResolvedProjectPath=B`. | The result includes a warning naming A and B; host binding remains canonical path A; the read does not bind or switch to B. |
