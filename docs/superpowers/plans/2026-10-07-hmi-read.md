# `hmi_read` (PR A) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Ship a read-only, batched `hmi_read` tool for the WinCC Unified engineering model. It has 20 typed operations and is built the same way as `plc_read`.

**Architecture:** The host gets a `TiaMcpServer/Hmi/` domain cloned from the `Plc/` read side and runs on the unchanged `StructuredOperationBatchExecutionEngine.ExecuteReadsAsync` and payload budget. One nested `HmiQueryInfo` carries every HMI parameter to the worker. The worker locates `HmiSoftware` the way `PlcSoftwareLocator` locates PLC software, and area readers enumerate the Unified compositions. CI compiles against a new generated `Siemens.Engineering.WinCCUnified` reference stub.

**Tech Stack:** .NET 10 host/tests/FakeWorker, net48 worker, netstandard2.0 contracts, ModelContextProtocol C# SDK, xUnit. No new package dependencies.

**Spec:** [hmi_read design](../specs/2026-10-07-hmi-read-design.md). Read it with this plan. Baseline: `main` at `94b6a72`. Branch: `feature/hmi-read`, which already carries the spec commit. PR B (a Unified `HmiTag` owner kind in `read_cross_references`) is **not** in this plan. Its target selector is a project-tree path, and `browse_project_tree` exposes no HMI nodes yet, so PR B gets its own addendum and plan after this PR merges.

## Global Constraints

- Tool counts go from 6/15/15 to **7/16/16** (read-only/read-write/full). `hmi_read` is registered alongside `plc_read` in `McpToolRegistration.WithAccessModeTools`, in every mode.
- `hmi_read(operations)`:
  - 1–50 items. Each item needs a unique non-blank `operationId` of at most 256 characters. Items are independent: a failed item does not stop the batch.
  - Annotations: `ReadOnly=true, Destructive=false, OpenWorld=false, UseStructuredContent=true`. `contractVersion "1.0"`.
- The operation names, fields, defaults and result fields are spec §2.2–§2.4, verbatim. Paging: `limit` 1–2000, default 500 (Task 0 may lower it); `offset` ≥ 0. Order: case-insensitive ordinal, with a case-sensitive ordinal tie-break.
- Errors come only from existing `WorkerFailureCategories`, as listed in spec §2.5. No new category.
- Budgets: 60,000 characters per value and 180,000 per document, through `StructuredOperationBatchPayloadBudget`. Values are omitted whole, never cut.
- Reads never bind, switch, open, save or close a project. They enumerate compositions and never call `Find`.
- The worker does not reference `Siemens.Engineering.WinCC.dll`. Siemens assemblies are never committed. Only the generated stub DLLs under `ref/` are.
- Out of scope (spec §1): SiVArc, plant views, YAML/JS export content, dynamizations/events, the generic attribute dump, compile, hardware-layer connections, Classic object reads.
- Commits: one short conventional line, no body or trailers, made after every implementation or fix step. Build and test serially (`-m:1`). Use PowerShell for `dotnet` commands that pass `/p:`. The 80% scoped coverage gate applies.
- No live TIA action without the maintainer's authorization naming the project. Never name the real project in docs.
- Documentation edits happen only in Task 10. The one exception is the acceptance reports and their index rows in Tasks 0 and 9. Code tasks keep `CiWorkflowTests` green against the unchanged docs.

## Decisions where the code shapes the design

| # | Code fact | Decision |
| --- | --- | --- |
| D1 | `OperationPolicyCatalog` is one flat namespace, and PLC already owns `list_tag_tables`, `create_tag`, `update_tag` and `delete_tag`. | Worker methods are `hmi_<operation>`, all `OperationCapability.Observe`. `HmiOperationCatalog.WorkerMethod(string operation)` is the only public→worker map. |
| D2 | `WorkerRequest` is a flat bag. Domains with many parameters use one nested object (`CrossReferenceSelector`, `NetworkObjectTarget`). | Add `WorkerRequest.HmiQuery : HmiQueryInfo?`. No new flat fields. |
| D3 | PLC reads go through one `OpennessWorkerClient` method each, built on `SendBoundProjectRequestAsync`. | Add a single `OpennessWorkerClient.ReadHmiAsync(string method, HmiQueryInfo query, string? projectPath)` on `SendBoundProjectRequestAsync`, with the same binding behavior as `ListTagTablesAsync`. |
| D4 | The worker dispatches by `method` in `Program.HandleLine`. | Add 20 explicit `"hmi_…" => ReadHmi(request)` cases. `ReadHmi` runs `WithProject` → `HmiReadDispatch.Read(project, request.Method, request.HmiQuery)` → `Success(payload)`. There are no prefix wildcards, because unknown methods must stay denied. |
| D5 | The Base stub already declares `MultilingualText`, `Language`, `LanguageSettings`, `ProjectBase`, `Software` and `SoftwareContainer`. | The new stub assembly contains only `Siemens.Engineering.HmiUnified.*` types. A Base member is added only if a reader needs one that is missing. |
| D6 | Tests link worker `.cs` files and run them against Siemens doubles declared in `Siemens.*` namespaces (`TestUtilities/*SiemensDoubles.cs`). | Add `TestUtilities/HmiUnifiedSiemensDoubles.cs`, which declares the same members as the stub (stub and doubles stay in step). Every new worker `Openness/Hmi/*.cs` file is linked into `TiaMcpServer.Tests.csproj`. |
| D7 | Classic `HmiTarget` lives in `WinCC.dll`. | Classic is detected by `software.GetType().FullName == "Siemens.Engineering.Hmi.HmiTarget"`. Task 0 S10 confirms the exact name. |
| D8 | `list_tag_tables` (PLC) returns `{ isComplete, messages }` and does not fail on one unreadable object. | Every HMI list or detail result carries `isComplete:bool` and `messages:string[]`. An unreadable property becomes `null` with a message and `isComplete:false`. An unreadable *composition* fails the item with `worker_operation_failed`. |
| D9 | `validate` paging is not specified (spec §2.3 #20). | `validate` pages over the **scanned objects** of the category in name order, which bounds the cost per call. `total` counts the category's objects. Findings are reported only for objects in the page. |
| D10 | `HmiText`/`HmiVariant` encoding depends on spike answers S3 and S5. | Task 0 writes the exact encoding table into its report. Tasks 4–5 implement it as written, and the spec gets a correction note in Task 10 if the report changes a shape. |

## Review Focus

1. **`hmiName` matching across two HMIs.** If `hmiName` matches HMI A's software name and HMI B's device name, the item fails with `target_ambiguous`; it never silently reads the first match. Pinned by `HmiSoftwareLocatorTests.NameMatchingSoftwareOfOneAndDeviceOfAnotherIsAmbiguous` (Task 3).
2. **Names that differ only in case.** Tags `Motor` and `motor` land on different pages in the same order on every call, so nothing is duplicated or skipped across pages. Pinned by `HmiPagerTests.CaseOnlyDifferentNamesKeepStableOrderAcrossPages` (Task 3).
3. **A `language` that is not a project language** (for example `fr-FR`). The item fails with `target_not_found`, and the message names the project languages. It does not return silently empty texts. Pinned by `HmiTextMapperTests.NonProjectLanguageFailsItemNamingProjectLanguages` (Task 3).
4. **One unreadable tag property out of 500.** The page is still returned: that field is null, there is a message, and `isComplete:false`. The item does not fail. Pinned by `HmiTagReaderTests.UnreadablePropertyNullsFieldAndMarksIncomplete` (Task 4).
5. **`validate category:"all"` on a large HMI.** One call scans at most `limit` objects and returns `nextOffset`, so it can neither time out nor blow the budget on a 10k-tag project. Pinned by `HmiValidationReaderTests.PagesOverScannedObjectsNotFindings` (Task 7).
