# PLC Write (PR B) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Ship `plc_write` on the guarded single-call pipeline, and retire `preview_write_batch`/`apply_write_batch`, the token core, the snapshot readers and `start_plc`/`stop_plc`.

**Architecture:** `PlcWriteDomain : IWriteDomain` runs through the unchanged `WriteExecution.RunAsync`, as `network_write` does. A host planner reads public evidence (the tag inventory, a project-tree snapshot and content exports) and applies an in-call overlay that sets `DependsOn`. The worker write methods take over the fail-closed rules from the snapshot readers before those readers are deleted.
**Tech Stack:** .NET 10 host/tests/FakeWorker, net48 worker, netstandard2.0 contracts, ModelContextProtocol C# SDK, xUnit. No new dependencies.

**Spec:** [PLC read/write and cross-references design](../specs/2026-10-05-plc-read-write-and-cross-references-design.md), §3.1, §3.3–§4, §6.2, Appendix A. Read the spec together with this plan. Baseline: `main` at `5286ea3` (PR A merged as #108). Branch: `feature/plc-write`.

## Global Constraints

- Tool counts: 6/16/16 now, 6/17/17 after Task 6, **6/15/15** after Task 7. Read-write and full expose identical tool lists.
- `plc_write(operations, dryRun=false)`:
  - at most 50 items, each with a unique non-blank `operationId` of at most 256 characters, run in caller order;
  - all items share one normalized `projectPath` (otherwise `validation_error`);
  - annotations `ReadOnly=false, Destructive=true, OpenWorld=false, UseStructuredContent=true`; `contractVersion "1.0"`.
- The 14 operations keep their names and their current field sets (`BatchOperationCatalog` specs), with two changes: `yamlContent` and `sourceContent` become `content`, and `update_block_logic` and `update_type_content` require `expectedContentHash`.
- Confirmation follows the Network model:
  - `ConfirmsEveryCall=false`; only `block` and `info` guards are registered; there is no elicitation in any mode or on `dryRun`.
  - The audit records confirmation `none` in read-write and `policy` in full.
- Every entered call writes exactly one audit v2 record to `writes-yyyy-MM-dd.jsonl`. No legacy audit is written.
- Budgets: 60,000 characters per value and 180,000 per document. Whole values are omitted; text, XML and JSON are never cut.
- `isError:true` only for a rejection before anything ran. A call that ran and failed returns `success:false`, `error:null`.
- Siemens calls stay in the worker. Siemens assemblies are never committed.
- Commits: one short conventional line, no body or trailers, committed after every implementation or fix step. Build and test serially. Use PowerShell for `dotnet` commands that pass `/p:`. The 80% scoped coverage gate applies.
- No live TIA action without the maintainer's authorization naming the project. Never name the real project in docs.

## Decisions where the code differs from the spec

Mapping `main` produced these decisions. They bind every task.

| # | Code fact | Decision |
| --- | --- | --- |
| D1 | `PlcOperationRequest`, `PlcOperationCatalog` and `PlcWorkerInvoker` already exist from PR A. | Extend them. Network shares one request DTO between read and write, and so does PLC. |
| D2 | The hash code is host-only `Safety/Pipeline/ContentHashes` and uses .NET 5+ APIs. | Add Contracts `ContentHashRules` (netstandard2.0). The host `ContentHashes` keeps `Check` and its records and delegates hashing to it, as do `WriteRun` audit hashing and `PlcContentHashes`. |
| D3 | `WorkerRequest` has `YamlContent`/`SourceContent` and no hash member. | Collapse them into `Content` and add `ExpectedContentHash`. |
| D4 | Worker writes report every precondition miss as `worker_operation_failed`. | Preconditions throw `WorkerOperationException` with these categories: missing target → `target_not_found`; several matches → `target_ambiguous`; hash mismatch, a collision, or an occupied create target found at mutation time → `state_changed` (the plan saw none, so the project changed); unreadable evidence → `worker_operation_failed`. |
| D5 | `PlcSoftwareLocator.Find` takes the first match among root devices only. | Add `FindUnique`, which considers every PLC including grouped devices. It replaces `Find` in `TagMutationService`, `TagTargetResolver`, `BlockMutationService`, `BlockTargetResolver` and `PlcTypeTargetResolver`. The two resolvers are shared with `plc_read`, so content reads become unique-PLC too; that keeps the hash a read issues and the hash a write checks on the same object. `CompileChecker` and `HardwareTagIndexResolver` are untouched. |
| D6 | #82: `BlockAddress.Parse` makes `PLC/Name` non-deterministic. | `Parse` stays unchanged. `create_block`, `create_block_group` and `delete_block_group` accept a deterministic path or the two-segment `PLC/Name`, which means the PLC root group. A one-segment path is `validation_error`. `update_block_logic` and `delete_block` resolve uniquely across the PLC. There is no root-group fallback anywhere, so `update_block_logic` on a missing block is `target_not_found`. |
| D7 | Inventory completeness exists only at the root. An unreadable constant is reported only as `Value == null`. PLC discovery swallows device-item errors. | If the root inventory has `IsComplete=false`, `plc_state_unverifiable` fires for every item. Task 2 makes discovery failures inventory messages. It also fires on update or delete of a constant whose value is null. |
| D8 | No host code decodes the write payloads. `PlcTypeImportResult` is internal to the worker. `update_block_logic` returns the bare text `"Import succeeded."`. | `TagMutationResultInfo` and `BlockMutationResultInfo` lose their marker. `PlcTypeImportResult` moves to Contracts as `PlcTypeImportResultInfo`. `update_block_logic` projects to a host-built `PlcBlockImportResult(Format, ImportOutcome)`; the raw text is not forwarded. |
| D9 | `ProjectTreeSnapshotWalker` drops unreadable nodes silently. The wire type is `ProjectTreeBrowseResultInfo`, which the host decodes into `ProjectTreeObservation`. | `Skipped` is added to `ProjectTreeSelectionResult`, `ProjectTreeFilter.Apply`, `ProjectTreeBrowseResultInfo`, the worker mapping, `ProjectTreeObservation` and the FakeWorker tree builders. The browse projection ignores it, so `browse_project_tree` output does not change. |
| D10 | `NetworkOperationCatalog` uses `WriteSafetyService.NormalizeProjectPath`. | Copy it to `Safety/Pipeline/WriteProjectPaths.Normalize` in Task 4. The old method delegates to it until Task 8. |
| D11 | `OperationBatchStatus` lives in `OperationBatchResult.cs`. `StandaloneToolResultFormatter` uses `OperationBatchPayloadBudget`. | Move `OperationBatchStatus` to its own file, and point the formatter at `StructuredOperationBatchPayloadBudget.MaxItemChars`, before the deletions. |
| D12 | The guard catalog is built in three places (`Program.cs:82`, `McpProtocolTestHarness:165`, `NetworkGuardedWriteFixture.CreateRunner`). | Add one `WriteGuardRegistration.ProductionCatalog()` in `Tools/McpToolRegistration.cs` and use it at all three sites. The fixture's Network-only constructor catalog stays. |
| D13 | Worker write handlers require `request.Confirm == true`. | Keep that gate. The client methods keep setting it. It is a dispatch gate, not consent. |
| D14 | `BatchPreviewDiff` is typed against deleted request types. | Move its algorithm and bounds to `Plc/PlcContentDiff`. `BatchPreviewDiff` becomes an adapter until Task 7 deletes it. |
| D15 | A dry run never blocks (`GuardDecisions.Decide`). | Keep it. A dry run returns `preview`, `success:true`, with block guards listed. The pipeline is unchanged. |
| D16 | The FakeWorker has no `start_plc`/`stop_plc` scenarios. | Nothing to delete there. |
| D17 | `LegacyNullOmissionReason.BatchRedesign` is used by test fixtures as well as payloads. | Remove `BatchRedesign`. The attribute and `ToolMigration` stay; the fixtures switch to `ToolMigration`. |

## Review Focus

1. An omitted or shared `plcName` that matches two PLCs, one of them in a device group, stops the whole call with `target_ambiguous` before anything runs. Today the first match is written silently. Pinned by `PlcWritePlannerTests.OmittedPlcNameWithTwoPlcsIsAmbiguous` (Task 5).
2. A `contentHash` copied from `plc_read`, in either format and also for a PLC in a device group, is accepted by `plc_write`; an edit made after the read is rejected with `state_changed`. Pinned by `PlcGuardedWriteDomainTests.PlcReadHashIsAcceptedThenDriftIsRejected` (Task 6).
3. A dry run that fires a block guard looks successful (`preview`, `success:true`, guard listed), and the actual call then blocks with nothing run. Pinned by `PlcGuardedWriteDomainTests.DryRunListsBlockGuardThenActualCallBlocks` (Task 6).
4. Callers still sending item-level `yamlContent` or `sourceContent`, or root `confirm` or `safetyToken`, get a rejection that names the replacement. They must not get a generic SDK binding failure. Pinned by `PlcGuardedWriteMcpTests.LegacyOrMalformedArguments_DoNotReachWorker` (Task 6).
5. When item 3 of 5 fails at the worker:
   - items 1–2 stay applied, items 4–5 are `skipped`, and item 3 carries `partial_write_no_rollback`;
   - verification covers attempted items only;
   - exactly one audit record is written.

   Pinned by `PlcGuardedWriteDomainTests.WorkerStateChangedFailsItemEarlierItemsStay` (Task 6).
